# 可观测性优化记录

> 2026-09-15。三处缺口都是先用探针在本地实测确认，再动手补的；
> 下面引用的输出都是真实运行结果，不是设想。

## 一、Sentry 装了、配了、但从来没被初始化

### 现象

`sentry-sdk[fastapi]` 在 `services/api/pyproject.toml` 里已声明，
`SENTRY_DSN` 也一路写进了三个地方：

| 位置                             | 内容                             |
| -------------------------------- | -------------------------------- |
| `.env.example:26`                | `SENTRY_DSN=`                    |
| `deploy/compose.yaml:22`         | `SENTRY_DSN: ${SENTRY_DSN:-}`    |
| `docs/腾讯云生产部署说明.md:134` | `SENTRY_DSN=<可选>`              |
| `app/core/config.py:42`          | `sentry_dsn: str \| None = None` |

但全项目搜不到任何一处 `sentry_sdk.init()`。也就是说：**运维照着部署文档
填了 DSN，Sentry 后台却一条错误都收不到，而且没有任何报错提示**——配置项
被静默忽略，看起来像是「接了监控」，实际等于没接。

### 修复

新增 `app/core/observability.py`，在 `create_app()` 里调用。三个取舍：

- **没配 DSN 直接跳过**，返回 `False`。本地开发和 CI 都不该往外发数据，
  这是正常路径而不是错误。
- **`traces_sample_rate`**：生产 0.1，其他环境 1.0。生产全量追踪又贵又吵，
  10% 足够看出接口级性能趋势；本地/预发量本来就小，全量采更好定位。
- **`send_default_pii=False` + `before_send` 二次清洗**。默认行为会把请求体、
  header、cookie 一起上报，里面有 `Authorization` 和学员手机号。只靠单一
  开关不稳妥——SDK 升级、或某处 `set_context` 手动塞了 headers，都可能把
  凭证带出去，所以 `_scrub_event()` 再显式抹一遍敏感 header
  （`authorization` / `cookie` / `set-cookie` / `x-api-key` / `idempotency-key`），
  并整体丢掉 `cookies` 和 `data`。

## 二、结构化日志里没有 request_id，访问日志完全缺失

### 现象

`app/core/logging.py` 的 structlog 处理链里一直有 `merge_contextvars`，
但**全项目没有任何地方调用过 `bind_contextvars`**——这个处理器等于空转。
后果是业务代码打出来的日志无法和具体请求关联：出错时只能看到一条孤立消息，
没法顺着 request_id 把整条链路串起来。

同时，请求级别的访问日志根本不存在，无法回答「这个接口 QPS 多少、
p99 多久、错误率多少」这类最基本的问题。

### 修复

改写 `app/core/http.py` 的 `request_id_middleware`：

- `clear_contextvars()` → `bind_contextvars(request_id=...)`。**clear 必须在前**：
  同一个 worker 协程会被复用，不清掉的话上一个请求绑的字段会泄漏到下一个
  请求的日志里。
- 每个请求输出一条 `http_request` 结构化日志，字段为
  `method` / `path` / `status_code` / `duration_ms`。
- 耗时用 `time.perf_counter()` 而不是 `time.time()`：后者受系统时钟调整
  影响，可能算出负耗时。
- 5xx 用 `warning` 级别，这样按级别过滤就能一次捞出所有服务端故障。
- **异常路径同样记日志**。`call_next` 抛出时若不记，请求就「进来了但没有
  任何记录」——这是最难排查的一种情况。
- `/health` 不记。`deploy/compose.yaml` 的 api healthcheck 是 `interval: 5s`，
  一天 1.7 万条全 200 的噪音会把真实请求冲掉。

### `_route_path()`：为什么不能用 `scope["route"].path`

日志里记的必须是**路由模板**而不是原始 URL——`/appointments/<uuid>` 这种
路径按原样记，日志聚合时每个 UUID 都会成为独立的一组，统计不出接口维度。

直觉做法是读 `scope["route"].path`，但实测（`fastapi 0.141.1 / starlette 1.3.1`）
发现拿不到完整路径：

```
app.routes 只有 6 项：4 个 docs 路由 + 2 个 _IncludedRouter
scope["route"]        -> APIRoute(path='/me')
scope["route"].path_format -> '/me'
```

原因是 **FastAPI 0.141 起 `include_router` 不再把子路由摊平到 `app.routes`**，
而是保留一个 `fastapi.routing._IncludedRouter` 节点，`scope["route"]` 拿到的
是叶子路由，`.path` 只有最后一段（`/api/v1/app/me` 变成 `/me`）。完整前缀
只藏在 `scope["fastapi"]["included_router"].include_context.prefix` 里——
那是私有属性，升级就可能失效。

所以改成从 `request.url.path` + `scope["path_params"]` 反查重建：两者都是
公开的 ASGI scope 键，不依赖任何框架内部结构。反查按值匹配且大小写不敏感
（UUID 在 URL 里大小写都合法，而 `path_params` 存的是原样字符串）；
路由没匹配上（404）时 `path_params` 为空，直接返回真实路径。

## 三、未捕获异常不符合项目自己的错误契约

### 现象

`app/schemas/error.py` 定义了统一错误契约 `{code, message, request_id}`，
`HTTPException` 和 `RequestValidationError` 都有对应 handler，但**没有兜底的
`Exception` handler**。实测一条必然抛异常的路由，Starlette 返回的是：

```
content-type: text/plain
body: Internal Server Error
（没有 X-Request-ID 响应头）
```

既不是 JSON，也不带 request_id——用户报 500 时，客户端拿不到任何可用于
定位的线索。

### 修复

新增 `unhandled_exception_handler`，注册在两个已有 handler **之后**
（它兜住所有未被前面处理的异常）。异常详情只进日志不进响应体——堆栈里
常有 SQL 和参数值。

注册前先单独验证过一个风险：**`add_exception_handler(Exception, ...)` 会不会
把现有测试里的真实 bug 吞掉**。结论是不会——现有测试套件用的
`ASGITransport(raise_app_exceptions=True)`（默认值）下原始异常照常抛出，
只有显式传 `raise_app_exceptions=False` 才会拿到这个 JSON 500。

## 四、测试：12 个用例，13 个变异全部拦下

`tests/test_observability.py`，与全量套件一起跑（73 passed / 2 skipped）。
新增两个模块覆盖率 `http.py` 93%、`observability.py` 96%。

绿灯不等于测试有效，所以跑了变异测试——逐个把实现改坏，看测试是否变红：

| #   | 变异                                     | 结果 |
| --- | ---------------------------------------- | ---- |
| 1   | 摘掉 `Exception` handler（回到裸 500）   | 拦下 |
| 2   | `create_app()` 不调用 `configure_sentry` | 拦下 |
| 3   | 不绑 contextvars                         | 拦下 |
| 4   | 不清 contextvars（请求间串号）           | 拦下 |
| 5   | `/health` 也记访问日志                   | 拦下 |
| 6   | `_route_path()` 退回原始路径             | 拦下 |
| 7   | 响应体带上异常详情                       | 拦下 |
| 8   | `send_default_pii=True`                  | 拦下 |
| 9   | `_scrub_event()` 不过滤 header           | 拦下 |
| 10  | 5xx 不用 warning 级别                    | 拦下 |
| 11  | 异常路径不记访问日志                     | 拦下 |
| 12  | 不回写 `X-Request-ID` 响应头             | 拦下 |
| 13  | 忽略客户端传来的 `X-Request-ID`          | 拦下 |

**第一轮只拦下 6 个**，2 / 4 / 6 存活。三个存活暴露的是真实的测试缺陷，
值得记下来：

- **变异 2**：Sentry 的两条用例都直接调 `configure_sentry()`，没有任何断言
  确认它被接进了 `create_app()`。删掉那一行调用，测试依然全绿——
  Sentry 静默失效，而这恰恰是这块代码要解决的问题本身。补了
  `test_create_app_wires_sentry`，并且断言传入的是 `get_settings()`
  同一实例（`lru_cache`，可以直接比身份）：若传临时构造的 `Settings`，
  线上 DSN 就读不到（作为变异 2b 单独验过，同样拦下）。
- **变异 4**：原用例在客户端关闭**之后**读 `get_contextvars()`，但中间件每次
  都会无条件绑 `request_id`，所以事后读到的永远是本请求自己的 id，串号
  根本看不出来。改成断言「访问日志实际带了什么」。
  污染源必须放在请求**之前**：探针实测确认 `BaseHTTPMiddleware` 把
  `call_next` 放进子任务，路由内部绑的字段传不回中间件，所以只有
  「外层已有残留」这个方向可观测——而它也正是真实的故障形态。
- **变异 6**：原用例只打 `/api/v1/app/me`，这个接口**没有路径参数**，模板和
  真实路径完全一样，用例根本分辨不出 `_route_path()` 有没有做还原。
  补了一条打 `/api/v1/app/schedules/{schedule_id}/appointments` 的用例。

补齐后又发现 10 / 11 / 12 也存活（都是实现注释里写了、却没有用例守住的
行为），一并补上。

> 过程中踩到一个坑值得记：第二轮里变异 7 / 8 显示「存活」，实际是
> `sed` 的缩进没对上、根本没改到文件。所以后续每个变异都加了
> `grep -q MUTANT` 确认真的应用了——**不然「测试没红」会被误读成测试无效，
> 而事实是变异根本没发生**。

## 五、还没做的

监控这一项里下面几块尚未落地，按优先级排：

1. **业务指标埋点**：预约成功率、消课异常率。现在只有请求级指标，
   看不到业务健康度。
2. **PostgreSQL 慢查询日志**：`deploy/compose.yaml` 当前没有配置任何
   `log_min_duration_statement`，慢 SQL 完全不可见。
3. **Redis 命中率与连接池监控**：连接池参数在
   `app/core/database.py` 里配好了（`pool_pre_ping` / `pool_recycle=1800`），
   但没有任何指标暴露，池耗尽只能靠超时报错反推。
