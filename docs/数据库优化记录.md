# 数据库优化记录

> 2026-09-15。所有数字都是在一个专门搭的基准库上实测的，不是估算。
> 基准库规模：5 门店 × 15 个月排课 = 6855 场课，21.7 万条预约，109MB，
> 状态分布按真实业务（completed 96%、reserved 2.2%、cancelled/no_show 各 ~0.9%）。

## 一、最重要的发现：模型少声明索引，下一次 autogenerate 会删掉生产索引

这不是性能问题，是一个**待爆的生产事故**，优先级远高于本来要做的索引优化。

### 现象

数据库里有 11 个复合索引（`ix_appointments_user_status_created`、
`ix_schedules_store_start_status`、`ix_products_public` 等），它们只写在
迁移文件里，ORM 模型的 `__table_args__` 完全没声明。

alembic autogenerate 以**模型**为唯一事实来源，模型里没有的索引一律判为
「已被移除」。实测跑一次：

```
$ alembic revision --autogenerate -m "probe"
INFO  Detected removed index 'ix_orders_user_store_created' on 'orders'
INFO  Detected removed index 'ix_products_public' on 'products'
...
生成结果：drop_index: 11   create_index: 11
```

也就是说，**任何人下次用 autogenerate 生成迁移并合并，生产上全部复合索引
会被一次删光**。没有报错、没有告警，只会在某天列表接口变慢时才被发现。
（那 11 条 `create_index` 在 `downgrade()` 里，不会救你。）

### 修复

把 11 个索引 + 2 个同样漂移的唯一约束补进模型声明：

| 文件                          | 补上的声明                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `app/models/appointment.py`   | `ix_appointments_user_status_created`、`ix_appointments_store_schedule_status`                   |
| `app/models/schedule.py`      | `ix_schedules_store_start_status`、`ix_schedules_teacher_time`、`ix_teachers_store_active_order` |
| `app/models/user.py`          | `ix_orders_user_store_created`、`ix_entitlements_user_store_status`                              |
| `app/models/product.py`       | `ix_categories_store_public`、`ix_products_public`、`uq_categories_store_name`                   |
| `app/models/store_content.py` | `ix_store_content_blocks_public`                                                                 |
| `app/models/admin.py`         | `ix_admin_user_stores_store_id`、`admin_users_username_key`                                      |

修完后 autogenerate 输出为空（`def upgrade(): pass`）。

有个坑值得记一下：`Table()` 里的 `Index()` 必须写在它引用的 `Column()`
**之后**，否则建表时列还不存在，直接
`ConstraintColumnNotFoundError`。

### 防回归

新增 `tests/test_schema_drift.py`，两个方向都卡：

- `test_no_index_exists_only_in_database` —— 库里有、模型没声明（会被 drop 的那类）
- `test_no_index_declared_only_in_models` —— 模型声明了、库里没有（缺迁移）

做过变异测试确认它真能拦住：删掉 `ix_schedules_teacher_time` 的声明后测试
立刻失败并指名道姓报出 `class_schedules: ix_schedules_teacher_time`。

## 二、新增管理端列表索引

迁移：`migrations/versions/20260915_0014_appointment_list_index.py`

```python
Index(
    "ix_appointments_store_status_created",
    "store_id", "status",
    text("created_at DESC"), text("id DESC"),
    postgresql_include=("schedule_id",),
)
```

### 为什么需要

`list_admin` 按 `store_id + status` 过滤，再 `created_at DESC, id DESC` 分页。
原来只有 `store_id`、`status` 两个单列索引。查 `completed`（生产上占绝大多数）
时，planner 只能用 `store_id` 单列索引捞出该门店**全部 4.4 万行**、
回表 5414 个块，再排序取 20 条。

### 实测（各跑 3 次）

| 查询             | 优化前                | 优化后                                    | 倍数  |
| ---------------- | --------------------- | ----------------------------------------- | ----- |
| 列表（LIMIT 20） | 9.7 / 9.7 / 10.3 ms   | 0.31 / 0.20 / 0.14 ms                     | ~60×  |
| 分页 `count(*)`  | 11.1 / 11.1 / 13.8 ms | 8.4 ms（Index Only Scan，Heap Fetches 0） | ~1.5× |

扫描行数 43851 → 20。索引体积 18MB。

### 两个设计取舍

1. **列顺序刻意和 ORDER BY 完全一致（含 DESC）**。实测对比过：升序索引靠
   `Index Scan Backward` 也能用（0.14~0.23ms），但计划里仍留一个 Sort 步骤；
   写成 `created_at DESC, id DESC` 后排序整个消失，索引读满 LIMIT 就停。
   两者体积相同，所以选完全匹配的写法。
2. **`INCLUDE (schedule_id)` 而不是把它放进索引键**。`count(*)` 要 join
   `class_schedules`，需要 `schedule_id`；放 INCLUDE 里能走 Index Only Scan
   不回表（11.1ms → 8.4ms），放键里则会白白增大索引且对过滤没用。

### 用 CONCURRENTLY 建

`appointments` 是热表，普通 `CREATE INDEX` 持 SHARE 锁会阻塞整张表写入。
迁移里用 `postgresql_concurrently=True` 包在 `autocommit_block()` 里
（CONCURRENTLY 不能在事务内执行）。已验证 upgrade → downgrade → upgrade 往返正常。

## 三、查过但**不需要**优化的地方（负面结论也记下来，省得重复劳动）

一开始的假设是「所有单列索引都该换成复合索引」。实测否掉了大部分：

| 查询                                          | 实测耗时     | 结论                                                                   |
| --------------------------------------------- | ------------ | ---------------------------------------------------------------------- |
| `list_user`（我的预约）                       | 0.03 ms      | 已被部分唯一索引 `uq_appointments_user_schedule_reserved` 覆盖，不用动 |
| `has_overlapping_reservation`（每次预约都跑） | 0.02~0.05 ms | 同上，不用动                                                           |
| 排课列表（门店+时间窗+状态）                  | 0.03~0.05 ms | `ix_class_schedules_starts_at` 够用，不用动                            |
| `list_admin` 查 `reserved`                    | 0.72~1.2 ms  | `reserved` 天然只占 2%，选择性已经够好                                 |

还有一条重要的方法论教训：**在 2.4 万行的表上，新增复合索引 planner 根本不选**
——全表只有 119 个堆块，全在内存里，顺序扫比走索引还快。我第一次建完索引
测出来「没有变化」，差点得出「索引没用」的错误结论。必须放大到 21.7 万行
（109MB，超出随手缓存的规模）才看得出 60 倍差距。

同理，第一轮测出的 26ms vs 0.27ms 里那个 26ms 是冷缓存假象。**每个方案都要
连跑 3 次看区间**，单次数字不可信。

## 四、还没做的

- [ ] 连接池监控（`pool_size` / `max_overflow` 的实际使用率没有观测手段）
- [ ] N+1 审计。仓储层普遍用 `selectinload` 显式加载，但
      `Appointment.user / schedule / entitlement / consumptions` 四个关系都是
      `lazy="selectin"`，任何一次 `select(Appointment)` 都会额外发 4 条查询，
      列表接口值得逐个确认是否都真的需要。
- [ ] `admin_users` 上 `admin_users_username_key` 和 `ix_admin_users_username`
      是两个语义重复的唯一索引（一个来自建表迁移的 `UniqueConstraint`，
      一个来自列上的 `unique=True, index=True`）。可以删掉一个，
      但属于独立的清理项，本次只如实声明、没有改动生产结构。
