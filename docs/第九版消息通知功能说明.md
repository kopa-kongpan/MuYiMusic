# MuYiMusic 第九版消息通知功能说明

## 1. 目标

建立统一“消息通知”能力，第一阶段覆盖：

- 学员预约或取消课程后，通知对应排课教师。
- 后台取消预约后，通知对应学员。
- 每日定时为次日仍处于已预约状态的学员生成上课提醒。
- 站内消息作为可靠保底，微信小程序订阅消息作为外部提醒渠道。

消息通知不得影响预约事务的一致性。业务事务只负责写入通知事件，异步任务负责外部投递、重试和审计。

## 2. 微信能力与前置条件

使用微信小程序登录和订阅消息：

1. `wx.login` 与服务端 `code2Session` 用于取得用户 `openid`。
2. `wx.requestSubscribeMessage` 必须由接收人主动操作并授权模板。
3. 服务端通过 `access_token` 调用 `subscribeMessage.send`。
4. 微信公众平台需准备新预约、预约取消、次日上课提醒模板及字段映射。

需要配置 `WECHAT_APP_ID`、`WECHAT_APP_SECRET` 和各模板 ID。真实密钥不得提交。普通一次性订阅通常授权一次可发送一次，因此微信不是唯一渠道；未授权或发送失败时仍保留站内消息。

## 3. 身份设计

微信身份与业务角色分离。同一用户登录后可拥有学员身份和教师身份。教师不能通过前端参数自行声明，必须由运营创建教师资料后完成受控绑定。

- `provider_accounts` 保存学员平台身份和 `openid`。
- `teacher_accounts` 保存教师与已有用户账号的绑定关系。
- 同一教师同一平台只能绑定一个用户账号；一个用户可在不同门店绑定不同教师身份。

教师工作台、一次性绑定码和教师专用权限属于第二阶段。本阶段先建立绑定模型和教师收件箱数据基础。

## 4. 数据模型

- `notifications`：站内消息，保存接收人、标题、正文、业务对象、已读时间。
- `notification_outbox`：外部投递任务，保存渠道、模板、状态、重试次数和失败原因。
- `notification_subscriptions`：用户对平台模板的授权结果，仅作为投递判断与审计，不替代微信实际额度。
- `teacher_accounts`：教师与登录用户账号的受控绑定。

所有业务事件使用稳定唯一键，例如：

- `appointment.created:{appointment_id}:teacher`
- `appointment.cancelled_by_user:{appointment_id}:teacher`
- `appointment.cancelled_by_admin:{appointment_id}:student`
- `appointment.next_day_reminder:{appointment_id}:student`

## 6. 验收标准

- 重复预约或重复任务不会产生重复消息。
- 预约事务回滚时通知也回滚；通知渠道失败不回滚已成功预约。
- 用户只能查看和操作自己的消息；教师收件箱不能被普通用户越权访问。
- 已取消预约不会生成次日提醒，跨时区计算统一按 `Asia/Shanghai`。
- 微信未配置、未授权、额度耗尽和网络失败均有明确记录，站内消息仍可读。
- migration、管理员初始化、API、长期服务、公开门店 API、管理后台和 H5 全链路通过本地 Docker 验收。

## 7. 当前边界

本版已交付站内通知、教师绑定与工作台、outbox 异步投递、次日提醒、后台投递运维和微信订阅适配。未配置微信凭据、模板或字段映射时，投递会安全跳过并保留站内消息及失败原因。真实微信发送仍必须等公众平台模板、合法域名和学生/教师双账号真机授权准备完成后验收。
