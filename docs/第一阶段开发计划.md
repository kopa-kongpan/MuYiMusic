# MuYiMusic 第一阶段开发计划

## 1. 计划原则

- 以 [第一阶段需求规格](./第一阶段需求规格.md) 为业务范围依据。
- 每个里程碑形成可演示、可测试的纵向闭环，不按“先写完全部后端，再写全部前端”的方式推进。
- 先解决门店数据隔离、认证权限、预约并发和消课审计等高风险基础问题。
- PDF 中标记为“待确认”的功能在产品确认前只保留扩展点，不进入实现。
- 新增或修改 API 时，同步生成 OpenAPI 客户端并完成调用方验证。

## 2. 实施优先级

| 优先级 | 里程碑 | 主要交付 | 前置条件 |
| --- | --- | --- | --- |
| P0 | 范围冻结 | 确认平台、地图、交易、预约、消课和个人中心边界 | 产品决策 |
| P1 | 公共基础与门店 | 认证权限、审计、媒体上传、门店后台、门店选择小程序 | P0 门店规则 |
| P2 | 首页内容闭环 | 首页内容后台、图片/视频展示、快捷入口 | P1 |
| P3 | 课程商品闭环 | 分类、商品、上下架、列表、详情、购买入口 | P1，交易边界确认 |
| P4 | 用户与课程权益 | 小程序登录、个人中心核心入口、订单与课程权益 | P3 |
| P5 | 排课、预约与消课 | 教师排课、可约资源、预约并发控制、消课和撤销 | P4，预约规则确认 |
| P6 | 联调与发布 | 双端适配、回归、安全、监控、数据备份和发布验收 | P1-P5 |

## 2.1 当前迭代：v0.1 门店闭环

状态：已完成，可本地联调与演示。实现和验证记录见 [第一版门店闭环说明](./第一版门店闭环说明.md)。

v0.1 只交付后续功能共同依赖的门店闭环：

- 管理员登录和基础权限校验。
- 门店数据模型、数据库 migration 和审计记录。
- 后台门店查询、创建、编辑、启停。
- 小程序门店搜索、选择和当前门店持久化。
- 公开门店 API 和后台门店管理 API。

课程、首页内容、购物车、预约和消课继续按照 P2-P5 推进，不在 v0.1 中使用模拟数据占位。

## 2.2 当前迭代：v0.2 首页内容闭环

状态：已完成，可本地联调与演示。实现和验证记录见 [第二版首页内容闭环说明](./第二版首页内容闭环说明.md)。

v0.2 已交付门店首页内容从后台维护到小程序展示的闭环：

- 图片、视频和快捷入口的创建、编辑、启停、展示时间和排序。
- 对象存储 S3v4 兼容直传签名、文件校验和门店对象 key 隔离。
- 平台管理员和门店运营的数据权限、`store_content:manage` 权限及审计。
- 小程序门店首页、媒体失败重试、快捷入口和四项底部导航。

课程商品、用户权益、预约和消课继续按照 P3-P5 推进，不使用模拟业务数据占位。

## 2.3 当前迭代：v0.3 课程商品闭环

状态：已完成，可本地联调与演示。实现和验证记录见 [第三版课程商品闭环说明](./第三版课程商品闭环说明.md)。

v0.3 已交付课程商品从后台维护到小程序浏览和本地购物车的闭环：

- 分类、商品、SKU 和商品图片模型，金额使用整数分。
- 商品草稿、发布、下架和归档状态流转，门店授权、权限与审计。
- 后台分类维护、商品查询、表单、预览、媒体直传和状态操作。
- 小程序分类、搜索、排序、列表、详情、数量、实时总价和门店级本地购物车。
- 加入购物车前实时校验门店、商品、SKU、数量和价格。

订单基础模型调整到 P4，与真实用户和课程权益一起建立；P3 不创建无用户归属的模拟订单。

## 2.4 当前迭代：v0.4 用户与课程权益只读闭环

状态：已完成，可本地联调与演示。实现和验证记录见 [第四版用户与课程权益说明](./第四版用户与课程权益说明.md)。

v0.4 已交付真实平台身份到本人数据查询的只读闭环：

- 微信真实换码、抖音换码适配和仅限本地环境的 H5 设备身份。
- 用户、平台账号、订单、订单项和课程权益模型，以及用户/管理员令牌类型隔离。
- 用户本人订单和课程权益查询，后台按权限与授权门店只读查询。
- 管理后台“用户与权益”工作台，以及小程序登录态个人中心、我的订单和我的课程。
- 我的课表和我的预约进入独立真实页面，P5 接入前不展示模拟数据。

第一阶段交易仍然只有本地购物车；v0.4 不提供订单、支付或课程权益写接口。P5 按已确认边界继续实现排课、预约和消课，预约细则须在相关状态与取消规则开发前确认。

## 2.5 当前迭代：v0.5 教师排课与可约资源闭环

状态：已完成，可本地联调与演示。实现和验证记录见 [第五版教师排课与可约资源说明](./第五版教师排课与可约资源说明.md)。

v0.5 先交付不依赖待确认预约细则的 P5 基础能力：

- 教师与排课模型、门店隔离、权限、审计和 migration。
- 后台教师维护、按日排课、教师时段冲突校验和排课状态流转。
- 公开可约资源查询，以及小程序按当前门店和未来 7 天展示真实排课。
- 公开结果统一过滤停用门店、停用教师、非开放、已结束和无剩余名额的排课。

预约提交、取消、缺席、课时扣减、消课和撤销仍未实现。统一预约视图的预约提前量、取消时限、冲突和缺席规则确认后，继续完成 P5 剩余纵向闭环。

## 2.6 当前迭代：v0.6 预约与消课闭环

状态：已完成本地容器验收。实现说明见 [第六版预约与消课闭环说明](./第六版预约与消课闭环说明.md)。

v0.6 已完成已确认规则下的 P5 剩余纵向闭环：

- 预约、用户取消、管理员取消、重叠时段、容量与权益有效期校验。
- 预约锁定课时，取消释放名额和锁定，正常到课与缺席在课后扣减。
- 独立权限的撤销消课，保留原记录、原因和审计，并恢复课时。
- 管理后台预约与消课工作台，小程序在线预约、我的预约、我的课表和权益锁定展示。
- 预约、取消、消课、缺席、撤销均具备幂等键和行锁；公开排课明确返回预约开放状态。

P5 的预约与消课功能已可进入 Docker 联调。P6 将执行全端构建、容器验收和发布准备。

## 2.7 当前迭代：v0.7 运营账号与后台运营增强

状态：已完成本地容器验收。实现说明见 [第七版运营账号与后台运营增强说明](./第七版运营账号与后台运营增强说明.md)。

v0.7 聚焦管理后台运营闭环：

- 新增平台管理员专属的子门店运营账号管理，包括角色、门店授权、启停和密码重置。
- 新增 `admins:manage` 权限和 `store_operator` 内置角色，默认权限不包含撤销消课。
- 运营账号列表、角色/门店选项、创建、编辑和密码重置 API 均写入审计并完成 OpenAPI 客户端生成。
- 课程商品已下架状态支持重新上架或归档，后端状态图和前端操作保持一致。

完成 v0.7 Docker 验收后，继续执行 P6 全端联调、安全回归和发布准备。

## 3. 里程碑交付内容

### P0 范围冻结

交付：

- 关闭需求文档第 12 节中会影响第一阶段设计的问题。
- 明确微信/抖音发布顺序和平台账号、域名、地图、对象存储等外部资源。
- 明确是否包含在线支付；若包含，补充订单、支付、退款和回调规格。
- 确认课程权益、预约取消、缺席和消课撤销规则。

完成门槛：

- 关键产品决策已有书面结论，预约细则保留到 P5 前确认。
- 产品验收主流程和第一阶段不做项得到确认。

### P1 公共基础与门店

后端：

- 统一响应错误码、请求追踪 ID、结构化日志和审计日志。
- 用户、平台账号、管理员、角色、权限和门店数据模型及 migration。
- 小程序登录、管理员登录、RBAC 和门店数据权限。
- 对象存储上传凭证接口和媒体元数据管理。
- 门店 CRUD、启停、搜索和距离计算所需接口。

管理后台：

- 管理员登录和基础布局。
- 门店列表、查询、创建、编辑、启停和地图坐标维护。

小程序：

- 微信/抖音登录适配器基础实现。
- 门店列表、关键词搜索、地图、定位降级、联系门店和进入门店。
- 当前门店状态管理和持久化。

完成门槛：

- 不同门店运营账号无法读取或修改未授权门店。
- 定位授权和拒绝授权路径均可选择门店。
- 门店状态、距离和切换行为通过 API 与前端测试。

### P2 首页内容闭环

状态：已完成，见 [第二版首页内容闭环说明](./第二版首页内容闭环说明.md)。

后端与后台：

- 门店首页内容模型和 migration。
- 图片、视频、快捷入口的创建、编辑、排序、启停和展示时间。
- 后台列表、表单、预览和排序操作。

小程序：

- 当前门店首页。
- 图片和视频内容流。
- 课程介绍、学员点评、师资团队和特惠活动入口。
- 加载、空内容、媒体失败和下架状态。

完成门槛：

- 后台调整内容后，小程序展示内容、状态和顺序一致。
- 不同门店内容完全隔离。

### P3 课程商品闭环

后端与后台：

- 分类、课程商品、SKU 和图片模型及 migration；订单模型随用户和权益在 P4 建立。
- 分类与商品 CRUD、查询、分页、上下架和归档。
- 商品公开列表、搜索、筛选、排序和详情 API。
- 创建购买请求时重新校验商品状态、价格和门店。

小程序：

- 课程分类、关键词搜索和综合/销量/新品/价格排序。
- 课程列表、详情、数量与总价计算、分享和联系门店。
- 按已确认交易方案实现立即购买；未确认支付前不得伪造支付成功。

完成门槛：

- 下架商品不能新购，历史订单仍可查询。
- 金额全部以整数存储和计算。
- 同一 OpenAPI 契约驱动后台与小程序类型。

### P4 用户与课程权益

后端与后台：

- 用户、订单和课程权益查询。
- 课程权益来源、总课时、剩余课时、有效期和门店归属。
- 后台用户与课程权益只读查询，人工调整需独立权限和审计。

小程序：

- 登录态个人中心。
- 我的订单、我的课程、我的课表和我的预约入口。
- 未登录拦截与登录后原路径返回。

完成门槛：

- 用户只能查看自己的数据。
- 门店运营只能查看授权门店的数据。
- 权益变化具备来源记录，不能直接覆盖剩余课时而不留痕。

### P5 排课、预约与消课

后端与后台：

- 教师、排课、预约和消课模型及 migration。
- 团体课容量、私教课单人时段和排课冲突校验。
- 可预约资源查询、预约提交、取消和状态流转。
- 消课、撤销消课、课时扣减和完整审计。

小程序：

- 门店、团体课/私教课、日期和日历筛选。
- 可预约教师、课程、时段、余量和空状态。
- 预约确认、结果和预约记录。

完成门槛：

- 并发预约不会超出容量。
- 重复请求不会重复占位或重复扣课时。
- 消课及撤销保持账目平衡并可追溯。
- 时区、跨日和过期权益场景通过测试。

### P6 联调与发布

- 微信和抖音开发者工具分别构建并验证。
- 真机验证定位、地图、登录、媒体、分享和网络异常。
- 完成后端 Ruff、mypy、pytest，前端 lint、typecheck、test 和正式构建。
- 验证权限越权、重复提交、上传限制、敏感数据脱敏和日志安全。
- 配置生产环境密钥、HTTPS 域名、对象存储、Sentry、数据库备份和恢复演练。
- 按需求文档第 11 节完成业务验收。

## 4. 单个功能的固定开发顺序

1. 确认业务规则和验收条件。
2. 设计数据模型并创建 Alembic migration。
3. 定义 Pydantic schema 和 OpenAPI。
4. 实现 repository、service 和 provider/platform 适配。
5. 实现 API 路由、认证、权限和审计。
6. 编写 service 单元测试和 API 集成测试。
7. 导出 OpenAPI 并生成 `packages/api-client`。
8. 实现管理后台或小程序界面。
9. 覆盖加载、空、错误、无权限和重复提交状态。
10. 完成相关质量检查和验收记录。

## 5. 建议首批任务顺序

1. 评审第一阶段需求和待确认项。
2. 定义统一错误响应、请求 ID 和审计事件。
3. 建立管理员、RBAC、用户、平台账号和门店 migration。
4. 实现后台登录与门店管理。
5. 实现小程序平台登录与门店选择。
6. 实现媒体上传和首页内容管理。
7. 实现课程分类、商品后台与小程序浏览。
8. 按确认方案实现订单及课程权益。
9. 实现教师排课、预约和消课。
10. 完成跨平台联调、安全检查与上线验收。

## 6. 每个里程碑的完成标准

- 需求和异常路径有明确验收条件。
- 数据结构变更包含可升级的 Alembic migration。
- API 权限、输入校验、错误码和审计完整。
- OpenAPI 客户端已重新生成，调用方无重复手写 DTO。
- 后端相关测试、Ruff 和 mypy 通过。
- 前端 lint、类型检查、测试和目标平台构建通过。
- 不使用模拟数据掩盖未完成后端。
- 文档、实现和测试描述一致。

## 7. 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 第一阶段范围未冻结 | 数据模型反复修改 | P0 先关闭交易、预约、消课和个人中心关键问题 |
| 平台账号或域名审批延迟 | 无法真机登录或发布 | 开发开始时同步申请，不等待功能完成 |
| 门店数据隔离遗漏 | 严重越权 | repository/service 强制门店范围并增加越权测试 |
| 并发预约超卖 | 名额和课时不一致 | 数据库事务、约束、锁和幂等键 |
| 消课可被随意修改 | 课程权益账目失真 | 不可变记录、撤销流程、独立权限和审计 |
| 图片/视频体积失控 | 加载慢、带宽成本高 | 上传限制、转码压缩、封面和 CDN 策略 |
| 参考界面被误解为全部范围 | 第一阶段延期 | 待确认功能不进入默认开发与验收 |
