# MuYiMusic 腾讯云生产部署说明

面向腾讯云**轻量应用服务器**，PostgreSQL 与 Redis 全部自建 Docker 容器，
Caddy 作为唯一公网入口并自动申请续期 Let's Encrypt 证书。

对应配置文件：

| 文件 | 用途 |
| --- | --- |
| `deploy/compose.prod.yaml` | 生产覆盖：收口端口、Redis 加密码、注入连接池、挂 Caddy |
| `deploy/caddy/Caddyfile` | TLS 入口与反向代理 |
| `deploy/scripts/backup-postgres.sh` | 全量备份，可选上传 COS，自动清理过期副本 |
| `deploy/scripts/restore-postgres.sh` | 从备份恢复，带二次确认 |

生产命令一律是两个 `-f` 叠加，缺一个都会退回本地不安全配置：

```bash
docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml <子命令>
```

## 一、采购清单

| 资源 | 规格 | 说明 |
| --- | --- | --- |
| 轻量应用服务器 | 通用型 2核4G，系统盘 40–60GB，Ubuntu 22.04 LTS | **必须包年包月且时长 ≥3 个月**，否则无法备案 |
| 域名 | 已购 | 需完成 ICP 备案 |
| COS 存储桶 | 与服务器同地域，私有读写 | 图片视频直传，同时存数据库备份 |
| TCR 个人版 | 免费 | 可选，缓解国内拉取基础镜像超时 |
| CDN | 回源 COS | 可选，有视频内容后再开 |

套餐选**通用型**而非存储型：数据库实测仅 11MB，全部镜像约 600MB，本地没有会持续增长的数据。

不需要买 TencentDB / 云数据库 Redis / 云联网 —— 数据库自建在同一台机器上，
轻量服务器不在自有 VPC 的那个组网限制因此完全不涉及。

## 二、部署前置

### 1. ICP 备案

买完服务器立刻提交。小程序的 `request` 合法域名只接受**已备案域名 + HTTPS**，
备案未通过前无法真机验收，只能用开发者工具勾选「不校验合法域名」调试。
管局审核通常 1–3 周，备案通过后 30 天内补办公安备案。

### 2. DNS 解析

在 DNSPod 添加 A 记录指向服务器公网 IP：

| 记录 | 用途 |
| --- | --- |
| `api.<域名>` | 小程序与 H5 调用的业务 API |
| `admin.<域名>` | 管理后台 |

**解析必须先生效**，否则 Caddy 首次启动申请证书会失败（HTTP-01 校验需要域名能回到本机）。
用 `dig api.<域名> +short` 确认返回服务器 IP 再继续。

### 3. 防火墙

轻量控制台防火墙只放行：

| 端口 | 来源 |
| --- | --- |
| 22 | 仅你的出口 IP |
| 80 | 全部（ACME 校验与 HTTPS 跳转） |
| 443 | 全部 |

**PostgreSQL 15432 与 Redis 16379 一律不要放行。** 它们在生产配置里只绑
`127.0.0.1`，本地访问走 SSH 隧道（见第七节）。

### 4. SSH 安全

整条运维链路的安全性建立在 SSH 上，建议创建实例时就配好密钥并关闭密码登录：

```bash
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo systemctl restart ssh
```

## 三、服务器初始化

```bash
# Docker 官方脚本（国内可用镜像源加速）
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"   # 重新登录生效

# 2核4G 加 2G swap，作为构建与峰值的保险
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

sudo mkdir -p /opt/muyimusic && sudo chown "$USER" /opt/muyimusic
git clone <仓库地址> /opt/muyimusic
```

## 四、生产 `.env`

以 `.env.example` 为模板，生产必改项：

```bash
APP_ENV=production

# 强随机值，逐个生成。POSTGRES_PASSWORD 与 REDIS_PASSWORD 会被拼进连接 URL，
# 用 hex 避免保留字符：openssl rand -hex 24
POSTGRES_PASSWORD=<强随机 hex>
REDIS_PASSWORD=<强随机 hex>
# 以下不进 URL，可用 openssl rand -base64 24
JWT_SECRET=<强随机>
ADMIN_INITIAL_PASSWORD=<至少 12 位>

# 生产域名
API_DOMAIN=api.<域名>
ADMIN_DOMAIN=admin.<域名>
ACME_EMAIL=<证书到期通知邮箱>
CORS_ORIGINS=https://admin.<域名>

# 并发。API_WORKERS 建议等于 CPU 核数
API_WORKERS=2
POSTGRES_MAX_CONNECTIONS=100
DATABASE_POOL_SIZE=10
DATABASE_MAX_OVERFLOW=20

WECHAT_APP_ID=<小程序 AppID>
WECHAT_APP_SECRET=<小程序 AppSecret>

OBJECT_STORAGE_PROVIDER=cos
# 其余 OBJECT_STORAGE_* 按 COS 控制台填写
SENTRY_DSN=<可选>
```

```bash
chmod 600 .env
```

有三个坑要留意：

1. **`APP_ENV=production` 会关闭 H5 的本地登录通道。**
   `app/providers/miniapp_identity.py` 里的本地换 token 分支仅在 `app_env == "local"` 生效，
   生产环境 H5 端无法登录。若仍需 H5 演示，需要另行接入正式登录方式。

2. **连接数要对得上账。** 上面这组值算出来是
   `2 workers × (10 + 20) = 60`，加 worker 容器与运维连接约 75，
   在 `POSTGRES_MAX_CONNECTIONS=100` 之内。调大 `API_WORKERS` 时必须同步核算，
   否则峰值会直接报 `too many connections`。

3. **`POSTGRES_PASSWORD` 不要含 URL 保留字符。**
   `compose.yaml` 把它原样插进
   `postgresql+asyncpg://<user>:<password>@postgres:5432/<db>`，
   密码里出现 `@ : / ? # %` 会破坏 URL 解析。
   用 `openssl rand -hex 24` 生成纯十六进制值最省事。
   注意在 `.env` 里单独设 `DATABASE_URL` 是无效的 —— compose 显式赋值优先。

## 五、首次启动

生产环境**不在服务器上构建前端镜像**：`deploy/frontend.Dockerfile` 要跑
`pnpm install` 加两次 webpack 构建（admin 与 H5），2核4G 会把内存吃满并拖垮 API。
推荐本地或 CI 构建后推 TCR，服务器只拉取。

先构建镜像（本地或 CI）：

```bash
docker compose -f deploy/compose.yaml build api admin h5
# 打 TCR tag 并推送，服务器侧改为 pull
```

服务器启动：

```bash
cd /opt/muyimusic
docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml up -d
```

`migrate` 与 `bootstrap` 是一次性容器，且 `api` 依赖
`bootstrap: service_completed_successfully` —— migration 失败时 API 不会启动，
这个 gate 是有意设计，不要绕过。

### 验证

```bash
# 全部容器状态，migrate/bootstrap 应为 exited(0)
docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml ps

# Caddy 证书申请日志。首次启动务必确认，失败通常是 DNS 未生效或 80 端口被拦
docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml logs caddy | tail -40

# 外网连通性
curl -I https://api.<域名>/health
curl -I https://admin.<域名>/

# 确认数据库端口没有对公网开放（应该拒绝连接或超时）
nc -vz <服务器公网IP> 15432
```

最后一条如果连上了，说明生产覆盖文件没生效 —— 检查命令里是否漏了
`-f deploy/compose.prod.yaml`。

## 六、备份

自建 PostgreSQL 没有 PITR，备份是必须项，第一天就要跑起来。
库只有十几 MB，全量备份便宜到可以每小时一次。

```bash
sudo mkdir -p /var/backups/muyimusic && sudo chown "$USER" /var/backups/muyimusic

# 先手动跑一次确认通路
deploy/scripts/backup-postgres.sh

crontab -e
```

```cron
# 每小时第 17 分备份，避开整点
17 * * * * cd /opt/muyimusic && deploy/scripts/backup-postgres.sh >> /var/log/muyimusic-backup.log 2>&1
```

要上传 COS，先装 `coscmd` 并 `coscmd config`，然后在 `.env` 设
`BACKUP_COS_PATH`。脚本会自动上传，未安装 coscmd 时打警告并跳过（不影响本地备份）。

另外在轻量控制台开**每日自动快照**，作为整机层面的兜底。

**每季度用 `restore-postgres.sh` 在测试环境真跑一次恢复。**
未经演练的备份等于没有备份 —— 恢复脚本会先停 api 与 worker 避免并发写，
再用备份自带的 `--clean --if-exists` 覆盖导入。

## 七、本地连接生产数据库

生产端口只绑回环，公网扫不到，用 SSH 隧道穿进去：

```bash
ssh -N -L 25432:127.0.0.1:15432 ubuntu@<服务器IP>
```

GUI 客户端（DBeaver / Navicat / pgAdmin，均内置 SSH 隧道配置页）连
`127.0.0.1:25432`，库名与账号取服务器 `.env` 的 `POSTGRES_DB` / `POSTGRES_USER`。

**本地端口特意用 25432 而不是 15432。** 本地 `.env` 的
`DOCKER_POSTGRES_PORT` 也是 15432，隧道若映到同一端口，
本地起 API 或手滑跑一次 `alembic upgrade head` 会直接操作线上库。

不需要 GUI 时，直接进容器更省事：

```bash
docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml \
  exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

## 八、小程序端配套

备案通过后：

1. **服务器域名白名单**（微信公众平台 → 开发管理）
   - `request`：`https://api.<域名>`
   - `uploadFile` / `downloadFile`：COS 或 CDN 域名（图片视频直传直连对象存储）

2. **重新构建小程序包**，把 API 基址烘焙成线上域名：

   ```bash
   TARO_APP_API_BASE_URL=https://api.<域名> pnpm build:weapp
   ```

3. **订阅消息模板**：在公众平台建 4 个模板，模板 ID 同时填到
   - 后端 `.env` 的 `WECHAT_TEMPLATE_*`
   - 小程序构建期的 `TARO_APP_WECHAT_TEMPLATE_*`

   两侧都留空时，`requestSubscribeMessage` 传空数组直接返回、
   后端投递安全跳过，站内消息仍可正常验收。
   服务类目需与教育培训对应，否则模板审核会被拒。

## 九、日常运维

```bash
# 统一前缀，建议写进 shell alias
alias dcp='docker compose --env-file .env -f deploy/compose.yaml -f deploy/compose.prod.yaml'

dcp ps                      # 状态
dcp logs -f api worker      # 跟踪日志
dcp restart api worker      # 改完 .env 后重启

# 发版：拉新镜像并滚动重启，migration 会先跑
dcp pull && dcp up -d
```

日志已配 `json-file` 轮转（单文件 10MB、保留 3 个），不会写满磁盘。
Caddy 的访问日志另外写在其 volume 内的 `/data/log/`。

建议在云监控配置告警：CPU、内存、磁盘使用率、以及实例状态。
`worker` 挂掉的故障很安静（次日上课提醒不再发送，但接口全部正常），
所以 `dcp ps` 里 worker 的状态值得单独盯。

## 十、后续扩容路径

当前架构的天花板远高于门店级流量：按 3 万注册、DAU 10% 估算，
日请求约 6 万，均值不到 1 QPS，峰值 20–30 QPS —— 2核4G 绰绰有余。

真正的压力点是**抢课瞬间**同一时段的行级写竞争，这类问题换更大机器收效有限，
需要从锁粒度和连接池解决。

需要横向扩展时的正确动作是迁移到 CVM（轻量不能原地升配成 CVM，需重装迁移），
届时再引入 CLB 与多 API 实例。数据库若需要 PITR 与主备切换，
迁 TencentDB 就是一次 `pg_dump` + `pg_restore`，不会被当前方案锁死。
